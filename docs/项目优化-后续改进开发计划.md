## 任务 1：密码加密（bcrypt）

### 1.1 现状

- [user.service.ts](../../question-server-nestjs/src/user/user.service.ts#L21-L30)：`create` 明文存 `password`，`findOne({ username, password })` 明文查。
- [auth.service.ts](../../question-server-nestjs/src/auth/auth.service.ts#L11-L15)：`signIn` 用 `findOne({ username, password })` 明文比对。
- [user.schema.ts](../../question-server-nestjs/src/user/schemas/user.schema.ts)：`password` 无加密。

### 1.2 方案

1. 引入 `bcryptjs`（纯 JS，避免 Windows 下 `bcrypt` 的 node-gyp 编译问题）。
2. `user.service.create`：`password` 先 `bcrypt.hash(password, 10)` 再入库。
3. `auth.service.signIn`：改为 `findByUsername(username)` 取用户，再 `bcrypt.compare(password, user.password)` 校验。
4. `user.service.findOne(query: { username; password })` 移除（或改为仅按 username），登录不再走明文比对。

### 1.3 决策点

- **bcrypt vs bcryptjs**：推荐 `bcryptjs`（跨平台省事，登录场景性能足够）。
- **存量用户密码迁移**（关键）：存量密码是明文，改 hash 后 `compare` 会失败。两种方案：
  - A（推荐）：一次性迁移脚本，把存量明文密码读出 → `bcrypt.hash` 重写回库。
  - B：登录时渐进迁移（先 `compare`，失败再明文比对，命中则重新 hash 存库）——更复杂，不推荐。

### 1.4 验收

- 新注册用户密码以 hash 存储（库中不再是明文）。
- 登录（新/存量用户）正常；密码错误返回「用户名或密码错误」。

## 任务 2：CORS 白名单限制

### 2.1 现状

- [main.ts](../../question-server-nestjs/src/main.ts#L10) 的 `app.enableCors()` 允许任意来源。

### 2.2 方案

`enableCors({ origin: 白名单 })`，白名单包含两个前端来源：
- `http://localhost:3000`（C 端 askflow-client）
- `http://localhost:5173`（管理端 AskFlow）

### 2.3 决策结论（已确认）

- 白名单来源：环境变量 `CORS_ORIGINS`（逗号分隔），`.env.example` 一并记录。

### 2.4 验收

- 两个前端正常跨域访问；其他来源（如 curl 模拟陌生 Origin）被拒。

## 任务 3：JWT 密钥生产强校验

### 3.1 现状

- [auth.module.ts](../../question-server-nestjs/src/auth/auth.module.ts) 的 `JWT_SECRET || 'xxYx&&111'`，忘配环境变量时静默用弱密钥。

### 3.2 方案

`useFactory` 里判断：`NODE_ENV === 'production'` 且无 `JWT_SECRET` 时抛错（或直接 `process.exit`），阻止用弱密钥启动。

### 3.3 决策点

- 校验位置：`useFactory` 内抛 `Error`（NestJS 启动失败）即可。

### 3.4 验收

- 生产环境缺 `JWT_SECRET` 启动报错；本地缺时仍用默认值（不影响开发）。

## 任务 4：AI 接口通用限流（暂缓）

> 实施受阻：`@nestjs/throttler@6.5.0` 仅支持到 NestJS 11（与项目 NestJS 12 冲突，装上后限流失效）；自实现 `RateLimitGuard`（`@UseGuards`）的 `canActivate` 未被调用（疑似 NestJS 12 行为变化）。已回退所有改动，待官方适配或改用中间件方案。

### 4.1 现状

- 仅有业务级「轮次上限 20」，接口级无限流。

### 4.2 方案

引入 `@nestjs/throttler`，对 `/api/ai/*` 做每用户（或 IP）限额（如每日 N 次），成本兜底防滥用。

### 4.3 决策点

- 限流维度：按用户（需解析 token）vs 按 IP（简单但可被代理绕过）。
- 限额值：如「每用户每日 50 次生成类 + 访谈按轮次已兜底」。

### 4.4 验收

- 超过限额返回 429；正常用户不受影响。
