## 任务 4：统计聚合下沉到数据库层

### 4.1 现状

- [stat.service.ts](../../question-server-nestjs/src/stat/stat.service.ts#L114-L169) 的 `getComponentStat` 用 `answerService.findAll(questionId, { page: 1, pageSize: total })` **全量拉取**答卷到内存，再在 JS 里循环累加各 value 计数。
- 答卷量增大时，`pageSize = total` 会把整份问卷所有答卷读进应用内存，属典型的内存型瓶颈。

### 4.2 方案

保留「查问卷 → 取组件 → 校验类型」的前置逻辑与「value → text」的后置映射，仅把中间的**计数累加**下沉到 MongoDB 聚合管道。

在 [answer.service.ts](../../question-server-nestjs/src/answer/answer.service.ts) 新增聚合方法（保持分层：stat 不直接操作 model）：

```ts
async aggregateComponentStat(questionId: string, componentFeId: string) {
  return await this.answerModel.aggregate([
    { $match: { questionId } },
    { $unwind: '$answerList' },
    { $match: { 'answerList.componentId': componentFeId } },
    { $project: { value: '$answerList.value' } },
    { $match: { value: { $ne: null, $ne: '' } } },
    // 多选值以逗号拼接，拆成数组后逐个计数
    { $project: { values: { $split: ['$value', ','] } } },
    { $unwind: '$values' },
    { $group: { _id: '$values', count: { $sum: 1 } } },
    { $project: { _id: 0, value: '$_id', count: 1 } },
  ])
}
```

[stat.service.ts](../../question-server-nestjs/src/stat/stat.service.ts) 的 `getComponentStat` 改为：

```ts
const counts = await this.answerService.aggregateComponentStat(questionId, componentFeId)
const list = counts.map(({ value, count }) => ({
  name: type === 'questionRadio' ? this._getRadioOptText(value, props) : this._getCheckboxOptText(value, props),
  count,
}))
```

### 4.3 顺带优化（可选，同属本任务）

- `_getRadioOptText` / `_getCheckboxOptText` 是 O(n) 线性查找（[stat.service.ts](../../question-server-nestjs/src/stat/stat.service.ts#L37-L58)），可预构建 `Map<value, text>` 降为 O(1)。数据量小时收益有限，作为附带优化。

### 4.4 决策点

- 聚合方法放在 `answer.service`（推荐，保持 stat 分层清晰）还是 `stat.service` 直接注入 `answerModel`？

### 4.5 验收

- `getComponentStat` 单选/多选结果与改造前完全一致（口径回归）。
- 对大数据量问卷，`findAll` 不再被调用，改走 `aggregate`；`explain` 确认命中 `questionId` 索引。

## 任务 5：反范式维护 `answerCount`

### 5.1 现状

- [question.schema.ts](../../question-server-nestjs/src/question/schemas/question.schema.ts#L57-L58) 已有 `answerCount` 字段，但注释明确「从未被维护」，恒为 0。
- [question.service.ts](../../question-server-nestjs/src/question/question.service.ts#L151-L164) 的 `findAllList` 每次列表查询都额外跑一次 `aggregate` 统计每份问卷的答卷数。

### 5.2 方案

1. 提交答卷时维护计数：[answer.service.ts](../../question-server-nestjs/src/answer/answer.service.ts) 的 `create` 在 `answer.save()` 后执行 `questionModel.updateOne({ _id: questionId }, { $inc: { answerCount: 1 } })`。
2. 列表查询去聚合：[question.service.ts](../../question-server-nestjs/src/question/question.service.ts) 的 `findAllList` 删除聚合统计，改为直接读取 `q.answerCount`。
3. 模块依赖：`answer.service` 需访问 `questionModel`，在 [answer.module.ts](../../question-server-nestjs/src/answer/answer.module.ts) 的 `MongooseModule.forFeature` 中增补 `Question` Model，并在 `AnswerService` 注入 `@InjectModel(Question.name)`。

### 5.3 决策点

- **存量数据回填**：历史问卷的 `answerCount` 均为 0，切换后列表会显示 0 直到有新答卷。三种策略：
  - A（推荐）：写一次性回填脚本/迁移，按现有 `answers` 集合统计回填所有问卷的 `answerCount`。
  - B：保留 `findAllList` 聚合作为兜底（新旧并存，复杂）。
  - C：直接切换，忽略存量（历史问卷计数暂不准，新答卷后恢复）。

### 5.4 验收

- 提交一份答卷后，对应问卷 `answerCount` +1；列表页答卷数即时正确。
- `findAllList` 不再跑聚合，列表查询只走一次 `find`。

## 任务 6：编辑器输入重渲染隔离

### 6.1 现状（问题链路）

属性面板输入 → `onValuesChange` → `changeComponentProps` dispatch → immer 更新 `componentList`（新引用）→ 所有订阅 `components` 的组件重渲染 → [EditCanvas.tsx](../../QD_Learn/AskFlow/src/pages/question/Edit/EditCanvas.tsx#L60-L96) 重渲染全部组件 → 同时 `redux-undo` 每次击键记录一个历史快照。

关键事实：
- [Component.tsx](../../QD_Learn/AskFlow/src/components/QuestionComponents/QuestionTitle/Component.tsx) 的导出**未用 `React.memo` 包裹**，父组件重渲染时全部子组件重渲染。
- [PropComponent.tsx](../../QD_Learn/AskFlow/src/components/QuestionComponents/QuestionTitle/PropComponent.tsx#L14-L18) 的 antd `onValuesChange` 是**每次击键**触发 dispatch。
- 但 immer 结构性共享保证了：未变化组件的 `props` 引用不变，这是 React.memo 生效的前提。

### 6.2 方案

**方案 A（推荐）：组件级 `React.memo` 隔离**

给 7 个 QuestionComponent 的 `Component.tsx` 默认导出用 `memo()` 包裹，如：

```tsx
import { memo } from 'react'
...
export default memo(QuestionTitle)
```

原理：immer 结构性共享使未变化组件的 `props` 引用稳定，`memo` 浅比较即可跳过未变化组件的重渲染。**不牺牲实时预览体验**，是收益/成本比最高的方案。

**方案 B（可选）：属性面板输入 debounce**

`PropComponent` 的 `onValuesChange` 改为本地 state + debounce 提交，降低 dispatch 频率。**代价是画布不再逐字实时预览**（改为停顿后更新），需权衡产品体验。

**方案 C（可选）：redux-undo 历史粒度**

对连续输入类 action 做历史合并（一步撤销而非逐字撤销），降低历史快照数量。

### 6.3 决策结论（已确认）

- 仅采用方案 A（`React.memo` 组件级隔离），保留逐字实时预览。
- 方案 B（属性面板 debounce）、方案 C（redux-undo 撤销粒度）不纳入本次。

### 6.4 验收

- 属性面板输入某一组件时，用 React DevTools Profiler 确认其余组件未重渲染。
- 输入流畅度改善，实时预览仍正常（若采用方案 A）。
