## 一、开发前分析（结合项目当前情况）

### 需求回顾

把"一页表单"变成 AI Agent 逐题对话：像聊天一样一题一题地问，根据前面的回答动态追问（如选了"不满意"追问"主要是哪方面"）。提交时把对话记录映射回 `answerList`，**后端存储和统计逻辑完全不用改**。

### 现状盘点

| 模块 | 现状 | 对本功能的影响 |
|---|---|---|
| C 端答卷页 | [id].tsx SSR 渲染表单，`<form action="/api/answer">` 原生 POST，无前端 JS 状态 | 需要新建**对话模式**页面/入口，与现有表单模式并存 |
| C 端技术栈 | Next.js 16.3.2（**pages router**）+ React 19，无 axios、无状态管理库、无 SSE 依赖 | 聊天 UI 需自建（纯 React state 即可）；SSE 用原生 `fetch` + `ReadableStream` 读取，**零新依赖** |
| 后端 AI 模块 | `chatWithRetry` 仅支持非流式（`response_format: json_object`）；openai SDK ^7.8.0 | 流式需新写一条**不走 JSON 契约**的调用路径（对话是自由文本，无需结构化输出） |
| 后端鉴权 | AuthGuard 全局生效（APP_GUARD），`@Public()` 放行答卷提交 | **关键矛盾：C 端答卷人无账号**，但 AI 接口必须鉴权（烧钱），见下方"鉴权设计" |
| 后端 CORS | `app.enableCors()` 全放行 | C 端（3000）直连后端（3005）SSE 无障碍 |
| 答卷存储 | `POST /api/answer` 只收 `{ questionId, answerList: [{ componentId, value }] }`，value 为 itemN 或文本 | 对话答案只要回填成同构 answerList，统计端零改动（与翻译功能同一铁律：value 不重写） |

### 关键难点与对策

**1. 鉴权：谁为对话式问卷的 LLM 调用付费？**

答卷人是匿名访客，无 JWT。AI 调用用的是**问卷作者**的 Key，意味着：
- 对话接口必须 `@Public()`（匿名可访问），否则 C 端无法使用
- 但 `@Public()` + 烧钱接口 = 被刷风险。对策（三层）：
  - 接口按 `questionId` 定位问卷 → 取**问卷作者的 aiConfig** 调 LLM（现有 5 个接口都是"登录用户自己的配置"，此处是第一个"用别人 Key"的接口，需在 service 层按 questionId 反查作者）
  - 服务端严格校验：问卷须已发布、未删除；`questionId` + 会话维度限流（内存 Map 简单节流，如同一问卷每 IP 每分钟 N 次）
  - LLM 入参完全由服务端从问卷数据生成（题目内容），用户输入仅作为对话上下文且截断长度——提示词注入面最小化

**2. 逐题对话的"状态"放哪？**

对话过程中 AI 需要知道：问到第几题、之前答了什么。方案：**状态放客户端**（React state），每次请求把「剩余题目 + 已答摘要」发给后端，后端无状态组装提示词。好处：后端不存会话、天然支持刷新重开、与现有无会话架构一致。

**3. 答案回填映射（需求原文的核心承诺）**

对话中用户对单选题答"第二个"，需映射回 `item2`。方案：**映射由前端确定性完成，不让 LLM 输出 value**——LLM 只负责"问什么、怎么追问"，每轮对话返回结构化的 `{ ask: 下一句问话, parsed?: { componentId, value } }` 中 `parsed` 由**前端**根据用户点选/输入确定。具体交互设计见技术选型。

## 二、技术选型（最适宜当前项目）

### 核心决策 1：对话形式 —— "结构化对话"而非"自由聊天"

| 方案 | 描述 | 取舍 |
|---|---|---|
| A. 自由聊天 | 用户打字，LLM 理解并记录答案 | 答案提取靠 LLM → 不可靠（统计端要求 value 精确） |
| **B. 结构化对话（推荐）** | AI 问出当前题 → 用户**点选项/输入文本**（真实表单控件嵌入聊天气泡）→ 前端确定性记录 value → AI 生成下一句问话（可结合上下文追问/跳题） | value 100% 可靠；"智能"体现在**问话文案、追问、跳题**由 LLM 流式生成；体验仍是聊天 |

选 B。LLM 的输入：问卷结构 + 已答摘要；输出（流式文本）：下一句问话 + 一个轻量 JSON 尾标记（跳题指令，如 `[[SKIP:n]]` 跳过 n 题 / `[[END]]` 直接收尾）。**答案本身永远不经过 LLM 输出**。

### 核心决策 2：流式方案 —— SSE 直连后端

- 后端新增 `POST /api/ai/chat`（`@Public()` + 自定义节流），`text/event-stream` 响应，用 openai SDK `stream: true` 逐 chunk 转发
- C 端 `fetch` + `ReadableStream` 手写 SSE 解析（~40 行，零依赖；不用 EventSource 因为它不支持 POST）
- **为什么不用 Next.js API route 代理**：现有 `/api/answer` 代理是同步重定向形态，SSE 透传需改造且多一跳延迟；CORS 已全放行，直连最简
- 降级：流式失败（个别供应商不支持 stream + response_format 组合）时接口可回退非流式一次性返回（后端一个开关逻辑，前端天然兼容——把整段文本当一次 chunk）

### 核心决策 3：入口与共存 —— 双模式切换

问卷页顶部加模式切换（`?mode=chat` 链接/"对话模式"按钮）：默认仍是表单模式（零回归风险），对话模式是独立路由 `[id].tsx` 同页条件渲染或 `/question/[id]/chat` 子路由。**推荐同页条件渲染**（复用 SSR 数据获取与错误态），切换是纯前端行为。

### 核心决策 4：追问与跳题的边界

- **追问**：LLM 对开放题答案可追问一轮（如答案太简短时"能具体说说吗？"），但**最多追问 1 次**且不产生新 answerList 项（追问答案覆盖原值）——防止无限对话刷 token
- **跳题**：仅支持 LLM 建议 + 用户确认（"这题可以跳过吗？"→ 用户点"跳过"按钮），LLM 不能自行丢弃必答题——必答校验铁律不破

## 三、技术可行性评估

| 项 | 评估 | 结论 |
|---|---|---|
| openai SDK 流式 | v7 支持 `client.chat.completions.create({ stream: true })` 返回 async iterable，chunk 累积即打字机文本 | ✅ 可行 |
| NestJS SSE | 用 `@Res()` 拿原生 response 对象，手写 `data: ...\n\n` 写入 + `Content-Type: text/event-stream`，无需 @nestjs/platform-socket.io 等新依赖 | ✅ 可行（Express 原生能力） |
| 全局响应拦截器冲突 | TransformInterceptor 会包装 `{ errno, data }`——SSE 接口必须**绕过全局拦截器**：用 `@Res()` 后 Nest 切换到"手动响应模式"，拦截器自然跳过 | ✅ 可行，但这是最易踩的坑，开发时重点验证 |
| 异常过滤器 | 流开始后的错误无法再改 HTTP 状态码，只能以 SSE `event: error` 事件下发，前端读流时处理 | ✅ 可行，需约定错误事件格式 |
| C 端 fetch 流读取 | React 19 + Next 16 pages router，`useRef` + `useState` 管理对话数组，onSubmit 里 fetch 流式读取循环 | ✅ 可行，零新依赖 |
| 答案映射可靠性 | value 由前端表单控件直接产生（与表单模式同源），LLM 不碰 value | ✅ 统计端零改动承诺达成 |
| 匿名鉴权成本 | 问卷作者 Key 被匿名访客消耗——用发布问卷即视为授权 + 限流兜底 | ⚠️ 可行但需限流，见取舍点 ① |
| 已有功能回归 | 表单模式代码路径不动（只加条件分支），后端 5 个 AI 接口不动 | ✅ 零回归 |

**总体结论：可行性高。** 无新依赖、无数据库改动、无统计端改动；新基建仅 1 个 SSE 端点 + 1 套前端聊天 UI；最大风险点是全局拦截器与 SSE 的冲突和匿名接口的滥用面，均有明确对策。

## 四、与既有 AI 功能的复用关系

| 既有资产 | 复用方式 |
|---|---|
| `requireAiConfig` | 不直接复用（它按登录用户取配置）；新写 `requireAuthorAiConfig(questionId)`：问卷 → 作者 username → 作者 aiConfig |

| 翻译功能的多语言 | 一期不做（对话语言跟问卷主版本）；`?lang=` 时对话模式入口隐藏，避免两套文案逻辑纠缠 |

## 五、接口契约设计

### POST /api/ai/chat（@Public + 内存限流）

入参：

```json
{
  "questionId": "xxx",
  "messages": [
    { "role": "assistant", "content": "你好，我们先从第一题开始..." },
    { "role": "user", "content": "[答:radio1=item2] 不满意" },
    { "role": "assistant", "content": "收到。主要是哪方面不满意呢？" }
  ],
  "componentId": "check1"   // 当前待答题目（服务端据此取题干与选项组装提示词）
}
```

- `messages` 里的 user 内容由前端拼装 `[答:fe_id=value] + 用户可见文本`，服务端**只信任自己的问卷数据**做 value 校验（value 必须是该组件合法选项），不信任 messages 内容本身
- 出参：SSE 流
  - `event: delta` `data: {"text":"..."}` 逐段问话文本（已剥离尾部标记）
  - `event: meta` `data: {"skip": 2}` 或 `data: {"end": true}`（问话文本末尾的 `[[SKIP:n]]` / `[[END]]` 标记由服务端解析后剥离再下发）
  - `event: error` `data: {"msg":"..."}`（流中错误，前端弹提示并可重试/转表单模式）
  - 流结束：`data: [DONE]`

### 提交答卷

复用现有 `POST /api/answer`（Next API route 代理），answerList 由前端对话 state 组装——**后端零改动**。

## 五-B、前端页面结构（C 端）

```
[id].tsx
├─ SSR: 问卷数据 + 作者 aiConfigured（新增字段，判断是否展示对话入口）
├─ 表单模式（默认，现有代码不动）
│   └─ 顶部模式切换条: [普通模式] [AI 对话模式]（aiConfigured=false 时只显示普通）
└─ ?mode=chat（同页前端状态切换）
    ├─ ChatQuestion 组件（新建）: 消息列表 + 底部"当前题作答区"
    │   ├─ 消息气泡: assistant 问话（打字机效果）/ user 答案摘要
    │   └─ 当前题作答区: 按组件类型渲染真实控件（radio 按钮组 / checkbox 组 / input / textarea）+ [跳过]（非必答时）
    ├─ 每答一题: 前端记录 { fe_id, value } → 组装 messages → fetch SSE → 打字机渲染下一句问话
    └─ 全部答完: 显示"提交"按钮 → 组装 answerList POST /api/answer → 跳 /success
```

### 开发点 6-1：后端（question-server-nestjs）

#### 6-1-1 `requireAuthorAiConfig(questionId)`——第一个"用别人 Key"的配置获取

```
findOne(questionId)
  → null → 404「问卷不存在」
  → isDeleted → 400「问卷不存在」（不暴露已删卷细节，与 C 端文案一致）
  → !isPublished → 400「问卷尚未发布」
  → userService.findByUsername(question.author)?.aiConfig
      → 无 → 400「该问卷未开启 AI 对话」
      → 有 → 返回 { apiKey, baseUrl, model }
```

与现有 `requireAiConfig` 的差异：入参从 username 变 questionId，中间多两道问卷状态校验。**单独新方法，不改旧方法**（旧的被 5 个接口用，零风险原则）。

#### 6-1-2 内存限流（service 层私有 Map）

```
Map<string, { count: number; windowStart: number }>
key = `${questionId}:${ip}`
规则：滑动窗口 60s 内最多 30 次；超出抛 429
```

- IP 取值：`req.headers['x-forwarded-for']?.split(',')[0] ?? req.ip`（开发环境无代理，req.ip 即真实 IP）
- 惰性重置：检查时若 `Date.now() - windowStart > 60_000` 则重置窗口；Map 本身不做定时清理（key 只增不减，问卷量级 < 几千时内存可忽略）
- 429 抛 HttpException 走正常异常通道（此时还没写 SSE 头，安全）

#### 6-1-3 `POST /api/ai/chat` SSE 端点（controller）

```ts
@Public()
@Post('chat')
async chat(@Req() req, @Body() body, @Res() res: Response) {
  // 1. 限流（429 走异常过滤器，未写 SSE 头，安全）
  // 2. 参数校验：questionId/componentId/messages（400）
  // 3. 取作者配置（400/404）
  // 4. 校验全部前置完成后才写 SSE 头：
  res.setHeader('Content-Type', 'text/event-stream; charset=utf-8')
  res.setHeader('Cache-Control', 'no-cache')
  res.setHeader('Connection', 'keep-alive')
  res.flushHeaders()
  // 5. 流式循环写 chunk + 结束 [DONE]
  // 6. 中途错误 → event: error 后 res.end()（不再抛异常）
}
```

**关键：校验全部在写头之前**——`@Res()` 手动响应模式下异常过滤器对已写入的响应无能为力；只有 LLM 流式过程中的错误才用 SSE error 事件。

#### 6-1-4 提示词与上下文组装

**System prompt**（`CHAT_SYSTEM_PROMPT`）：
- 角色：亲切的问卷访谈员，正在与答卷人逐题对话
- 规则：一次只问一题；自然口吻复述题干与选项（radio 可列选项让用户口头选）；当前题刚被回答过时可就其答案**追问一次**（回复以 `[[STAY]]` 结尾，前端停留在原题、答案覆盖）；开放题答案过于简短（<5 字）可引导补充；必答题（题目列表已标注）不得建议跳过；余下题目无需再问时可输出 `[[END]]` 收尾；非必答题用户无意愿回答时可建议跳过并输出 `[[SKIP:1]]`；追问仅限开放题；标记只能出现在回复最末尾，一次最多一个
- **不承诺输出 JSON**（与既有 5 个接口的契约模式根本不同）

**User prompt**（每轮动态组装，全部来自服务端问卷数据）：

```
问卷标题: xxx
题目列表（含已答状态）:
1. [单选][必答] 您的性别是？选项: 男/女 —— 已答: 女
2. [多行输入][选答] 其他建议 —— 未答（当前待问）
3. [多选][必答] 喜欢的口味？选项: 酸/甜/辣 —— 未答
...
对话记录（最近 10 轮）:
assistant: ...
user: ...
请开始问第 2 题。
```

- `messages` 入参**双保险**：每条 user 消息的 `[答:fe_id=value]` 用服务端问卷数据校验（fe_id 存在、value 是该组件合法选项），非法直接 400——防伪造对话历史刷 Key
- messages 截断：最多保留最近 10 轮 + 单条消息截 500 字
- `componentId` 校验其存在于可见题目列表

#### 6-1-5 流式调用与标记解析（`streamChat`）

```
client.chat.completions.create({ model, messages, stream: true, temperature: 0.7 })
for await (chunk of stream) {
  text = chunk.choices[0]?.delta?.content ?? ''
  buffer += text
  // 标记解析状态机：检测到 "[[" → 暂存后续字符直到 "]]" 闭合
  //   是 [[SKIP:n]] / [[END]] / [[STAY]] → 缓存为 pendingMeta，不下发
  //   不是合法标记 → 原样作为正文补发
  // 无标记前缀的 buffer 前段 → 安全下发 event: delta
}
// 流结束：pendingMeta 存在 → event: meta（{ skip } / { end } / { stay }）→ [DONE]
```

- SDK `stream: true` 返回 `Stream<ChatCompletionChunk>`，async iterator 逐 chunk 取 `delta.content`
- **降级路径**：供应商对 `stream: true` 报错（BadRequestError 且 message 含 stream）时，改非流式一次性把全文当一个 delta 下发——前端无需改动
- 中途错误：`mapLlmError` 映射后写 `event: error` + `res.end()`

#### 6-1-6 `GET /api/ai/chat-status/:questionId`（C 端入口判断小接口）

- `@Public`，返回 `{ chatEnabled: boolean }` = 已发布 && 未删除 && 作者 aiConfig 存在 && **无 translations**（取舍点 ③）
- 实现放 `AiService.isChatEnabled(questionId)`，挂 ai.controller——计划原定挂 question.controller，因 AiModule 已导入 QuestionModule，QuestionModule 反向导入 AiService 会造成模块循环依赖，改挂 ai.controller（路径 `/api/ai/chat-status/:questionId`）

### 开发点 6-2：前端（askflow-client）

#### 6-2-1 `[id].tsx` 改造（SSR + 模式切换）

- `getServerSideProps` 增调 `getChatStatus(id)`（新 service，调 ai-status 接口），Props 增 `chatEnabled`

#### 6-2-2 `ChatQuestion.tsx`（新建）

**State 机**：

```
type Msg = { role: 'assistant' | 'user'; content: string }
state: msgs（对话记录）/ answers: Record<fe_id, string>（answerList 素材）
       curIndex（当前题下标）/ curPhase: 'asking' | 'answering' | 'finished'
       streamText（正在流式输出的问话）
```

**流程**：
1. 挂载自动发起第一轮：fetch SSE → streamText 逐 chunk 追加渲染（尾部闪烁光标）→ 完成后问话入 msgs，`curPhase='answering'`
2. 作答区按 `componentList[curIndex]` 类型渲染**受控原生控件**（不复用现有 getComponent——那是非受控表单组件）：
   - radio → 单选按钮组，**点选即答**（立即进入下一题，聊天感最强）
   - checkbox → 多选按钮组 + "确认"按钮（多选需明确提交时机）
   - input/textarea → 原生输入框 + "提交"按钮
   - 非必答题显示"跳过本题"链接
3. 作答/跳过 → 组装 `[答:fe_id=value]` 或 `[跳:fe_id]` 追加 user 消息 → curIndex 前进（skip 按 meta 指令额外前进）→ **自动发起下一轮**（全自动，无"下一题"按钮）→ 重复
   - 追问协议：每轮请求的 componentId = 前端当前停留题。收到 `meta.stay` → curIndex 不前进（作答区保持该题，答案覆盖原值）；前端记录每题 stay 次数，同一题第二次收到 stay 强制忽略并前进（落实"最多追问一次"）
4. `meta.end` 或题目问完 → `curPhase='finished'`，显示"提交问卷"按钮
5. 提交：answers → answerList（**跳过的题不产生项**，与表单模式不填一致）→ POST 现有 `/api/answer` → redirect `/success`
6. 追问轮：作答区仍是普通输入框（追问只体现在问话文案，用户无感），答案**覆盖**原值（取舍点 ④）

**SSE 客户端**（~40 行工具函数）：

```
fetch(url, { method: 'POST', body, signal })
  → res.body.getReader() 循环 read()
  → TextDecoder 解码 → 按 '\n\n' 切事件块 → 解析 event:/data: 行
  → 回调 onDelta(text) / onMeta(meta) / onError(msg) / onDone()
```

- AbortController 挂组件 ref，卸载中止（防泄漏 + 离开页面仍写 state）
- 失败重试：onError 后作答区上方显示"网络波动，[重试] / [切换普通模式]"

#### 6-2-3 样式（ChatQuestion.module.scss，新建）

- 消息区：左气泡（assistant 灰底）/ 右气泡（user 蓝底白字），最大宽 75%
- 打字机：streamText 尾部跟随闪烁光标（CSS animation，chunk 直接追加，不做逐字动画）
- 作答区：卡片式（白底圆角阴影），按钮组按组件 isVertical 配置
- 布局：**消息区视口高度内滚动（flex: 1; overflow-y: auto），作答区固定底部**——聊天 UI 惯例

#### 6-2-4 提交数据口径（统计端兼容的关键）

| 组件类型 | answers[fe_id] 值 | 与表单模式一致性 |
|---|---|---|
| radio | `item2`（选项 value） | ✅ 同构（value 均来自 props.options） |
| checkbox | `item1,item3`（逗号拼接） | ✅ 同构（QuestionCheckbox 也是 toString()） |
| input/textarea | 用户输入原文 | ✅ 同构 |
| 跳过的题 | 不产生 answerList 项 | ✅ 同构（表单模式不填也不提交该字段） |
| 结构组件（title/paragraph/info） | 不进对话流程也不产生项 | ✅ 同构（无表单 name） |

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 全局 TransformInterceptor 干扰 SSE | `@Res()` 手动响应模式绕过；开发首步先用最小 SSE demo 验证 |
| 匿名接口被刷（作者 Key 被烧） | 内存限流（questionId+IP）；消息长度截断；问卷须已发布；后续可加"作者可关闭对话模式"开关（一期不做，见取舍点 ②） |
| LLM 忽略指令连续追问/跳必答题 | 提示词硬约束 + 前端兜底：必答题无"跳过"按钮，LLM 输出 SKIP 对必答题忽略（前端校验 isLocked） |
| 流式中断（网络/供应商） | 前端显示"重试"按钮（重发当前轮）；连续失败 2 次提示"切换到普通模式" |
| 打字机效果与流式 chunk 边界 | chunk 直接追加渲染（不做逐字动画，流式本身已是渐进显示，逐字动画是过度设计） |

## 八、已确认取舍点（用户已确认，2026-09-03）

| 取舍点 | 已确认方案 |
|---|---|
| ① 匿名限流策略 | **内存 Map（questionId+IP，每分钟 30 次）**——单机部署足够，零新依赖 |
| ② 作者侧开关 | **一期不做**——所有已发布问卷 + 作者已配置 AI 即显示对话入口（如需关闭，二期加 `chatEnabled` 字段 + B 端设置项） |
| ③ 对话语言 | **仅主版本中文**——有 translations 的问卷对话入口隐藏，避免两套文案逻辑纠缠 |
| ④ 追问深度 | **开放题最多追问 1 次**——不产生新 answerList 项（追问答案覆盖原值），防无限对话刷 token |
| ⑤ 历史对话持久化 | **不持久化**——刷新即重新开始，与表单模式行为一致 |
